## What is here

* `negative/<name>.json`: 61 negative fixtures. Each is `kind: investigation` (schemas/negative-fixture.schema.json) with
  `expectedErrorCode: CAUSA.HISTORY_INADMISSIBLE` and `expectedDomainCode` equal to the oracle's first `HISTORY.*` code.
* `valid/<name>/<investigationId>/{manifest.json,events.ndjson,snapshot.json}`: four valid histories. Each passes all
  17 reader stages. The extra `<investigationId>` level is required because the directory name must equal the
  manifest `investigationId` (CONTRACT §11.1 stages 1 and 8).
* `MATRIX.json`: one row per fixture, `{id: "AC-SUP-<name>", kind, input, covers, errors, expected}`. `input` is relative
  to `requirements/causa/data/v1.0.0/`. `errors` is the **complete ordered** `History.validate` list that the oracle
  returns: the history code and the inner rule code, or `null` when the group is not a refusal (§15.2 2.2, 2.3, §15.6).
  `expected` is what a consumer must print (ACCEPTANCE §3). For valid rows it also carries `stateSha256`,
  `eventsSha256`, `version` and `lifecycle`.

## How the fixtures were built

1. **Base.** Every fixture starts from a frozen valid investigation of `causa-data@causa-storage-v1.0.0`, read only. It
   uses either the whole history or a prefix cut at a command-group boundary, which is admissible by construction.
2. **New groups.** One or more command groups are appended at the end. Only the last group is meant to be
   inadmissible. Groups placed before it (for example "admit evidence", "weaken hypothesis") are admissible, and the
   oracle confirms this. Three fixtures need another shape: `sup-start-group-reconstructs-finding` adds an event to
   group 1, `sup-confirm-in-draft` drops the activation group, and `sup-no-start-single-group` is a one-event history.
3. **Canonical files.** These make stages 1–14 pass:
   - RFC 8785 lines;
   - versions `1..N`;
   - `eventId` re-derived (CONTRACT §5.2);
   - a fresh UUIDv5 `correlationId` per new group;
   - `occurredAt` 2 minutes apart;
   - a manifest consistent with the events.

   Negative fixtures keep the frozen snapshot of the same investigation. It is stale, but inadmissible histories stop
   at stage 15. Valid histories get the snapshot and manifest of the clean-room consumer's projection
   (CONTRACT §8.1, §9.1).
4. **Acceptance conditions.** A fixture is accepted only when all three hold:
   - the oracle's error list equals the declared `errors`: **exactly one** error unless the row is a documented minimal
     co-firing set;
   - the inner code in the oracle message (`would be refused now (CODE)`) is the intended rule;
   - the clean-room consumer reports the same `primaryCode` and `domainCode`, with `admissibility: evaluated`. For valid
     rows it must report `primaryCode: null` and the recorded `stateSha256`.

Regenerate and re-verify:

```sh
python3 -I tools/causa-contract/differential/supplementary.py generate --causa-data <causa-data at causa-storage-v1.0.0>
DOTNET_ROOT=<dotnet> python3 -I tools/causa-contract/differential/supplementary.py check \
    --causa-data <root> --oracle <built oracle binary> [--json report.json]
```

`check` also fails when any file on disk differs from what `generate` would write. Last run: 65/65 rows agree with
the oracle and the clean-room consumer.

Repetition refusal (§10.27). These fixtures use ASCII-only text, so they do not depend on platform lower-casing
(§17 E-5). They are refused after trim (spaces and tabs) and case folding:

- negative knowledge: `sup-agent-repeats-negative-knowledge`;
- a falsified hypothesis: `sup-agent-repeats-falsified-normalised`.

`sup-valid-repetition-not-refused` shows proposals that are **not** refused:

- human and system actors;
- kinds `unknown` and `action`;
- an interior double space (only the ends are trimmed);
- a missing final period;
- the statement of a hypothesis that is not falsified.

LF-only framing: `sup-valid-unicode-line-separators` holds verbatim text (an observation, evidence content, a
relationship rationale, a hypothesis statement and mechanism) with raw U+0085, U+2028 and U+2029. RFC 8785 does not
escape these, so they appear unescaped inside `events.ndjson` lines (30 LF-terminated lines; `str.splitlines()` would
see 41). A reader that splits on anything but LF fails this history.

## Findings for SEMANTICS.md

1. **§15.9.3 / §15.9.5 omit `INVESTIGATION.EXISTS`.** §15.9.5 says every code not listed can be the first inner code
   after stages 1–14. `INVESTIGATION.EXISTS` cannot be, because the envelope schema pins `InvestigationStarted` to
   `aggregateVersion: 1`. The oracle produces `INVESTIGATION.EXISTS` for a later `InvestigationStarted` group, but both
   attempted fixtures stop at stage 7 in the clean-room consumer, which is the correct reader verdict.
2. **§15.9 does not mention `INVESTIGATION.NOT_FOUND`.** It is reachable after stages 1–14, but only at group 1, through
   the §15.3 precedence (`sup-start-group-reconstructs-finding`).
3. The §14 note and §15.9.4 claims about co-firing (`NO_CONFIRMED_CAUSE`, `BLOCKING_UNKNOWN`, `MEMBER_MISSING`) were
   confirmed against the oracle with the minimal sets above.

## Limits

* The oracle checks admissibility only. The valid histories' snapshot, manifest and `stateSha256` come from the
  clean-room consumer's projection (CONTRACT §8). No engine projection checks them independently.
* `MATRIX.json` is a pinned requirement file (`parity_gate.py` `PINNED_REQUIREMENTS`). Regenerating it requires a
  reviewed update of `compatibility/release-pin.json` `requirementsDigests`.
