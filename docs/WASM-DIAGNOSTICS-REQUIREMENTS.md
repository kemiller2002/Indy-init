# WebAssembly Runtime Diagnostics Requirements

Status: normative engineering requirements for Causa and subsequent Indy Init builds. Added after Rehearsal 4 (defect D-HIST-WASM) for the baseline that follows BL-CAUSA-INDY-INIT-aab8f80c7743. It does not apply to Rehearsal 4 or change its acceptance. The remediation brief's identifier REQ-WASM-DIAG-001 is WASM-DIAG-001 in this document.

## WASM-DIAG-001: Runtime diagnostics for the .NET WebAssembly engine [P0]
The build MUST provide a diagnostics configuration of the .NET WebAssembly engine that enables Microsoft's EventPipe diagnostics (EnableDiagnostics, EventSourceSupport and MetricsSupport), so that managed heap dumps, CPU samples and metrics can be collected with the runtime's documented browser APIs. The diagnostics configuration MUST NOT be the deployed production build. A runtime failure MUST be capturable with browser developer tools, including the JavaScript and WebAssembly call stack of the failure, using an unstripped native runtime or its symbol map so that WebAssembly frames can be named. Managed memory diagnostics MUST include heap dumps and garbage-collection activity before and after the failing operation where the runtime supports them. Runtime performance profiling MUST be available through EventPipe CPU sampling or browser performance profiling, and each capture MUST record its duration and the operation it covers. Exceptions and runtime failures MUST be captured with the exception type, message and stack, and the engine's state after the failure (usable or stopped) MUST be recorded. Every diagnostic record MUST identify the .NET SDK, runtime and WebAssembly workload versions, the build configuration and execution mode (interpreter or AOT, and runtime options), the browser name and version, and the exact source commit. Diagnostic evidence MUST be reproducible: the inputs, the build variant and the commands that produced it MUST be recorded so that another person can repeat the capture and obtain comparable results. Diagnostic artifacts MUST be handled as sensitive: they MUST NOT contain credentials or tokens, MUST be scanned for token-shaped strings before they are uploaded or published, and MUST NOT be kept in public locations longer than needed. Where practical, the capture and its checks MUST run automatically in CI, on a branch or workflow that does not affect the acceptance pipeline; where automation is not practical, the reason MUST be recorded.

## Implementation
Place implementation work items in the target repository's documented Praxis input folder, not GitHub Issues. This document adds requirements only; it does not assert that any build has implemented them.
