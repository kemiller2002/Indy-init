**Status: PROPOSED.** This model is authoritative only if the owner approves ODR-V413-02 (AMENDMENT-DECISION.md). It changes no frozen file.

**Where it comes from.** It makes concrete the payload types that v4.1.2 left opaque ("each payload type is the domain owner's to define"). It uses the shapes the background `docs/FSHARP-TYPE-SHAPES.md` already describes (sections 3, 5, 15, 19–21, 27) and adds only what the content workflow needs and no document defines.

**The exact F#** is `proposed/00-DOMAIN-STUBS.proposed.fs`, a drop-in replacement for the v4.1.2 `contracts/00-DOMAIN-STUBS.fs`.
- **Typecheck:** it builds with every other frozen contract file unchanged (`01-IF41-DOMAIN.fs` … `99-Usage.fs`), with `TreatWarningsAsErrors` (FINAL-READINESS.md §Validation).
- **Specification preflight:** Percepta passes over the full specification with it (5 machines, 101 transitions, 25 invariants, 26 operations, 134 catalog commands, 109 types).

## Principles kept from the frozen design

- **Event-sourced, append-only.** Every change is a new event in the investigation's history. Nothing is overwritten. Original text stays in the history, as R2.4-O1, R15.4-O1, UI-005-O2 and STATE-TRANSITION-TABLES§4-evidence-lifecycle-O9 require.
- **One persistence path.** The existing GitHub save protocol (SM-SAVE, PERSIST-006/007 read-back) persists the events. No new database, store or infrastructure is added.
- **Stable identity.** Every entity gets a GUID identity when it is created (R1.3-O1, R9.9-O2), generated by the application, never derived from the text. A name or text edit never changes it.
- **Provenance on every payload.** Each record carries the actor, kind and time, plus the source reference (FSHARP-TYPE-SHAPES §5, reduced; R3.2-O1, D-002-O1).
- **The domain's gates are unchanged.** Resolution still requires the review, evidence and causal-analysis gates. Recording a conclusion records a snapshot; it does not resolve the investigation (STATE-TRANSITION-TABLES§14-conclusion-behavior-O1).

## Contract changes against v4.1.2

These are the changes ODR-V413-02 would approve:
1. **Content payloads made concrete.** `NonEmptyText` (private constructor), the IDs and the records above replace the opaque `class end` stubs. The case names of `CoreCommand` and `CoreEvent` are unchanged.
2. **Five new `CoreCommand` cases:** `ReviseInvestigationDetails`, `ReviseObservation`, `ReviseHypothesis`, `ReviseEvidence` and `RecordConclusion`.
3. **Five new `CoreEvent` cases:** `InvestigationDetailsRevised`, `ObservationRevised`, `HypothesisRevised`, `EvidenceRevised` and `ConclusionRecorded`.
4. **Not changed:** `CommandEnvelope`, `EventEnvelope`, `Investigation = { Id; Version }` and every other interface.

**Alternative with no contract change (ODR-V413-02 option B).** The revisions and the conclusion travel as the existing `Command.Extension of SemanticId * payloadJson` and `EventPayload.ExtensionEvent`, under registered semantic IDs. It is weaker: the payloads are untyped JSON at the boundary, and Percepta cannot check them.

## Validation rules

These belong to the domain's smart constructors. The UI shows them as field errors.

| Rule | Where |
|---|---|
| Title, observation text, hypothesis statement, evidence label, evidence description and conclusion statement are non-empty after trimming | `NonEmptyText.create` |
| SourceUrl is an absolute `http`/`https` URL; anything else is refused and never rendered as a link | `SourceUrl.create`; UI-005-O3 sanitising |
| A relationship's Evidence and Hypothesis exist in this investigation | `decide` refuses with a blocker |
| A revision names an existing entity of the same kind | `decide` refuses |
| A duplicate submission (same CommandId) is idempotent | the existing duplicate detection by event ID (`Decision.Duplicate`) |

## Projection and persistence

- **Projection.** The investigation projection keeps maps by ID (FSHARP-TYPE-SHAPES §30). For each entity:
  - the current fields come from its latest record or revision;
  - its revision history is the ordered list of its events.
- **Wire.** The wire carries the full `EventPayload.CoreEvent` body, so a reload from GitHub and a replay reconstruct every field. EXT-DATA-008-O2 and STORAGE-002-O1/O2 ("reconstruct by replaying events") already require replayability. CONTENT-009 makes the content part of what must survive.
