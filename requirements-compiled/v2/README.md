## Why v2 exists

The v1 package changed after the Rehearsal 4 freeze without a new version: its manifest went from `0cd4c3f5…` (the R4 freeze record) to `b771cd40…` (the R5 freeze record) across `5d69cca`, `f9219d1` and `4b38213`. History is not rewritten. The changes are recorded in `readiness/evidence/v1-post-freeze-changes.json`, v1 stays as committed at `459f65a`, and this change is cut as v2. Rule from now on: a change to any file of a package that a rehearsal freeze record names is a new package version.

**v1 is no longer regenerated by the current compiler**, because the plan now carries acceptance contracts. To reproduce v1, use the compiler at `459f65a`.

**What differs from v1:** in content, only `verification-plan.json`, `requirements-validation-report.json` (the V18 title) and `package-manifest.json`. Every other generated file is byte-identical to v1.

## The acceptance contract (per obligation)

Each obligation in `verification-plan.json` keeps every revision-1 member. It also gains `tokens` (the baseline value tokens, verbatim) and `acceptanceContract`:

| Member | Meaning |
|---|---|
| `requirement`, `obligation`, `obligationId`, `priority` | Requirement id, baseline obligation id, stable `VPO-` id and priority. |
| `verificationMethod` | The requirement's gates and verification-rule ids. |
| `requiredEvidenceCategories` | A set drawn from `unit`, `integration`, `browser`, `live-provider`, `security`, `accessibility`, `independent-acceptance`. |
| `categoryDerivation` | For each required category, the ids of the declared rules that require it. |
| `testIdentity` | `bound` with exact tests `{id, kind, categories}` from `curation/verification-plan.json` `testBindings`, or explicitly `unbound`. Tests are never invented. |
| `dependencies` | Requirements and contracts whose change invalidates the evidence. |
| `freshness` | `policy` is the strictest of the requirement's policy and the policies its categories impose (`live-provider`: live per commit; `independent-acceptance`: review per commit). |
| `verificationStatus` | `unverified`, `unclassified` or `excluded`. The plan never says `verified`; only `verify-plan` can, from evidence. |
| `missingCoverage` | One entry per uncovered category, with a reason: `no-bound-test`, `no-evidence`, or `unclassified` when no rule reaches the obligation. |

### Categories come from a table, not from code

`curation/evidence-categories.json` lists 14 rules. Each one names the existing requirement data it rests on: a verification rule id, a gate, a document, a requirement selector, a title pattern, an obligation kind, an obligation id or a freshness policy. Each rule also cites its source verbatim. An obligation requires the union of the categories of every rule that applies to it.

An obligation that no rule reaches is `unclassified`. It is reported as missing coverage and is never given a default.

The plan embeds the table (`evidenceCategories`, with its sha256), so a consumer can re-derive every contract from the plan alone.

At this baseline the measured distribution, by obligation, is:

No P0 obligation is satisfied by unit evidence alone. This is the Rehearsal 5 `5dcb91e` lesson: engine tests do not prove UI, provider or live obligations.

## How agents consume the plan before implementation

1. **Pin the plan.** Pin it by `planIdentity.digest`; Ordo reads it unchanged (it ignores unknown members).
2. **Read each obligation's contract before writing code.** `requiredEvidenceCategories` is what the obligation's tests must prove, and `freshness.policy` is how fresh that proof must be.
3. **Bind tests before claiming them.** For each obligation, the owner adds a binding to `curation/verification-plan.json` `testBindings` and recompiles; agents do not write approvals (RDP-003). A binding has the form `{obligation, tests: [{id, kind, categories}]}` and names only the categories the test fully proves for that obligation. A test that proves only part of an obligation is bound with only those categories; it is not tagged as proving the whole obligation.
4. **Report per obligation.** Each `causa.acceptance-evidence/1` file lists `obligations: [{id: <VPO id>, verification, tests: [{testId, outcome}]}]`, and the ledger row lists exactly the bound tests.
5. **Read `verify-plan`'s per-obligation result.** It gives `verificationStatus` and `missingCoverage` for every obligation; anything short of `verified` is work left.

## Validation

- `readiness/evidence/r4-r5-baseline-validation.json` compiles the plan against two baselines:
  - **Rehearsal 4:** the frozen baseline regenerated at `aab8f80`. All 108 P0 requirements and 326 P0 obligations are represented, each with a contract.
  - **Rehearsal 5:** the baseline R5 pins (Indy-init `459f65a`), checked against every R5 pin.
  
  The two baselines are byte-identical, and so are the two plans. Both rehearsals' committed derived documents were compared obligation by obligation:
  - R5 carries 461 of 461 requirements and all 326 P0 obligations verbatim, with 0 differences. The rows of 67 documents are ordered differently from the baseline.
  - R4 carries 456 of 461 requirements and all 326 P0 obligations verbatim. The 5 it does not carry are its requested non-P0 exclusions.
- `readiness/evidence/r4-verification-plan-replay.json` replays the verifier pipeline over Rehearsal 4's published evidence against this plan. The R4 ledger names tests that the plan never bound, so every case is now INVALID with `TEST-MAPPING` diagnostics. The other expected diagnostics (`STALE-EVIDENCE`, `UNAUTHORIZED-EXCLUSION`) and per-requirement statuses still appear.
