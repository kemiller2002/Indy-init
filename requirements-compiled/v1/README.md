# Compiled requirements package v1

This package compiles the Causa requirements into a structured form. Every part is traceable to its sources, and everything that is generated can be regenerated byte for byte. It exists so that the next rehearsal and the event **execute a validated plan** instead of rediscovering how to build the application.

|   |   |
|---|---|
| Source | kemiller2002/indy-init `9dc7d575f9d981e2be6f83543e18f548332e1a53`. The compiler builds the baseline at this commit itself, with the F# port of the baseline generator. |
| Other repositories | the exact commits in `curation/sources.json` (also in `package-manifest.json`) |
| Compilation verdict | **PASS**: every check V01–V17 passes, including V14 (no baseline drift) |
| Rehearsal readiness | **BLOCKED**: 5 blockers, all upstream releases, listed in `requirements-validation-report.json`. The executed preflight gives BLOCKED; see `readiness/READINESS-REPORT.md`. |
| Target run | the repository's **Rehearsal 4** (write-path dress rehearsal). The mission brief called it "Rehearsal 3" (F-020). |

Two things this package does not do:
- **It does not change any authoritative requirement.** `docs/` and `requirements/causa-requirements-baseline.json` are unmodified.
- **It does not mark anything implemented or verified.** Every requirement is `not-verified` and every verification entry is `NOT_RUN`.

## How to read it (agents: start here)

1. **Read the readiness blockers first.** They are in `requirements-validation-report.json` → `rehearsalReadiness`. While any remains, the slice it touches stops; this is the ADRP-001 conflict stop.
2. **Use the decision registry.** `decision-registry.json` lists what is already decided; do not re-decide a `fixed-architectural` entry. `unresolved` entries belong to the owner.
3. **Execute a plan.** Take `execution-plan-resource.json` (default; matches R4-03) or `execution-plan-time.json` (needs the owner approval in F-007). Each task's `completion` conditions and `gates` are its definition of done.
4. **Use the verification manifest per requirement.** `verification-manifest.json` says which gate and owner verify each requirement and what evidence they need. Evidence is reused only under the `defaults.evidenceReuse` rule.
5. **Fetch the original wording.** `requirements-inventory.json` has the verbatim text. The normalized file deliberately carries only ids.

## Regenerate

The compiler is F# (.NET SDK 10.0.402, `tools/requirements-compiler`). It reads every repository through `git show <commit>:<path>`, so working-tree edits cannot leak in.

```bash
# 1. Checkouts containing each commit listed in curation/sources.json (shallow clones are enough)
K=/path/to/checkouts
REPOS=$(for r in causa-data praxis ordo dokimos percepta forma limen folio echelon-registry conditor \
  indy-init-rehearsal-001 indy-init-rehearsal-002 indy-init-rehearsal-003; do printf -- '--repo %s=%s/%s ' $r $K $r; done)
RC="dotnet tools/requirements-compiler/src/bin/Release/net10.0/requirements-compiler.dll"
dotnet build tools/requirements-compiler/tests -c Release

# 2. Compile (exit 0 PASS, 3 FAIL, 2 unusable input), or verify the committed package (exit 4 on any difference).
#    The baseline is built in-process at the recorded indy-init commit; `--baseline FILE` supplies one instead.
$RC --source . --committed-baseline requirements/causa-requirements-baseline.json \
  --curation requirements-compiled/v1/curation --out requirements-compiled/v1 $REPOS [--check]

# 3. Rehearsal 4 preflight: executes every check and writes evidence (exit 0 READY, 3 BLOCKED or FAIL)
$RC preflight <same options as step 2> --evidence requirements-compiled/v1/readiness/evidence/preflight-run.json

# 4. Baseline generation alone (same contract as tools/build-requirements-baseline.py)
$RC baseline . <40-hex commit> > baseline.json

# 5. Tests: offline (CI) and full (negative controls, determinism, committed-package check)
dotnet run -c Release --no-build --project tools/requirements-compiler/tests -- --offline --source .
dotnet run -c Release --no-build --project tools/requirements-compiler/tests -- <same options as step 2, without --check>
```

**Determinism.**
- Objects keep a fixed key order and lists are sorted ordinally.
- Output is ASCII JSON with two-space indentation and a trailing newline.
- Nothing reads a clock, the network or the working tree.
- The test suite compiles twice and compares the bytes, then runs `--check` against this directory.

**Tests.** The offline mode, which CI runs in job `fsharp-tooling`, checks two things: that the F# baseline port reproduces the committed Python-generated baseline byte for byte, and the ported unit cases. The full mode also injects 17 defects, and each one must fail its named check:
- a non-verbatim citation;
- a dependency cycle;
- a requirement in no work item;
- an unsourced fixed decision;
- an over-claimed contract;
- an identity mismatch;
- a conflict that names a fixed decision;
- a conflict "resolved" without a source;
- an unknown reference;
- a wrong repository revision;
- an undefined Percepta metric;
- a requirement with no verification rule;
- a tampered baseline obligation;
- an unclassified readiness blocker;
- an open decision without a recommendation;
- a recurring defect class without a failing-first test;
- a preflight task that depends on a timed task.

**For a new run** (for example after owner decisions, or at the kickoff re-pin, T01):
1. Update the commits in `curation/sources.json`, and the decision and finding statuses the owner has decided.
2. Compile, then fix every failing citation or reference the compiler reports. When a requirement text changes, V11 rejects the old quotes, so the curation cannot silently go stale.
3. Re-run the preflight.
4. `v1` is updated in place until the Rehearsal 4 kickoff. Publish the frozen kickoff state as `v2/`.

## Mechanical rules (no judgement)

- **Inventory.**
  - Baseline requirements come from `praxis.requirements-baseline/1` exactly. V01 checks that every obligation occurs verbatim in its document at the source commit.
  - External documents are sectioned at headings of levels 1–3. Each section runs to the next heading, and its obligations are its sentences, list items and table rows.
- **Modality.** RFC 2119 words, and imperative prohibitions ("never", "do not"), as written. Modality is never promoted.
- **Flags.**
  - `PRIORITY-UNSTATED`, `PRIORITY-IN-TITLE-ONLY`, `ACCEPTANCE-CRITERIA-MISSING`, `MODALITY-UNMARKED`, `VAGUE-TERMS` (fixed word list in `src/Text.fs`).
  - Informational: `ERROR-HANDLING-UNSTATED` and `ACCESSIBILITY-NOT-LOCAL`. These are keyword rules, so a hit is a prompt to look, not a defect.
- **Overlaps.**
  - Exact duplicate obligations of at least four words.
  - Structural containment: a section that repeats every obligation of another, which is how the baseline treats level-1 sections.
  - Near duplicates: content-word Jaccard of at least 0.6.
  - Semantic overlaps across documents are analyst findings F-022…F-029. Each requirement keeps its own disposition. The overlap tells a derivation to implement and evidence once, then map the result to every id.
- **Review.** A requirement is `flagged-for-review` when a material unresolved finding names it, or when it carries a major flag.

**Smallest additional tooling, proposed but not built.** A `derive` mode for requirements-compiler would emit two things in the rehearsal repository's Praxis requirements location:
- a draft Praxis RQ markdown package, with one criteria table per requirement carrying the exact tokens;
- a `praxis.requirements-disposition/1` skeleton, `preserved` with one criterion per obligation.

This would remove the hand transcription that lost UI-016 in Rehearsal 3. It must still leave `needs-review` obligations for a person, and it must never write approvals. Build it only after F-004 settles the gate's released format.

## Limits

- Findings, decisions, contracts and tasks are analyst judgements. The compiler proves that their citations are verbatim at the recorded commits and that their references resolve. It does not prove that the judgement is right; that needs a person.
- Contract status is at most `identity-verified`. No integration has been exercised.
- Plan steps are unit steps, so they order the work but do not estimate time.
- The full compilation and the full test suite need local checkouts of the 14 repositories in `curation/sources.json`. CI runs only the offline subset: the baseline port, its units, and the cross-check against the Python generator.
